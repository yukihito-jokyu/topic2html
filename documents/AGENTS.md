# AI Development Workflow

このリポジトリでは、要件定義から実装までをPlanning領域とImplementation領域に分離する。

## Planning Requests

要件整理、Feature分割、Initial Design、Feature Design、Task分割、進捗再開を依頼された場合は `planning-orchestrator` を起点にする。

Planning領域では `.ai/workflow/artifact-map.yaml` のArtifact Ownershipを必ず守る。
OwnerではないSkillが成果物を直接修正してはならない。

## Decision Policy

`.ai/workflow/decision-policy.md` を共通判断基準とする。

- L1/L2: 原則AIが自走する
- L3: 人間承認
- L4: 人間との議論・決定

不明点があるだけで停止せず、局所的・可逆・検証可能ならAssumptionを明示して進める。

## Planning / Implementation Boundary

Planningは `features/{feature_id}/implementation-handoff.yaml` の完成で終了する。

Planning Skillは、承認済み設計で固定されていない限り以下をTaskへ埋め込まない。

- file path
- function/class/symbol名
- framework API
- library-specific implementation

これらはImplementation領域で決める。

## Implementation Skills

実装に必要なTechnology-specific Skillが不足している場合は `implementation-skill-builder` を使う。

実装が親リポジトリで行われる場合、生成Skillは親リポジトリの `.agents/skills/impl-<scope>/SKILL.md` に配置する。`documents/` 配下で実装する場合だけ、この階層の `.agents/skills/impl-<scope>/SKILL.md` に配置する。
1 TaskごとのSkill生成は禁止する。

## Skill Problems

Skillの過剰質問、誤った出力、Ownership違反、Task粒度問題、誤発火などが起きた場合は `skill-maintainer` を使う。
Project Artifactを手でねじ曲げてSkill不具合を隠さない。

## 人間の指摘からの継続的改善

人間から成果物、説明、質問、レビュー、進行、または判断の仕方について指摘を受けて対応した後は、毎回、その原因が個別成果物だけにあるのか、AGENTS.md・workflow policy・Skillの規約不足にもあるのかを判定する。

- 再発可能な規約不足なら、`skill-maintainer` を使い、最小の正規ルールと regression scenario を修正・追加する。
- プロダクト固有または一回限りの内容なら、Skillを不必要に一般化せず、対象成果物だけを修正する。
- SkillやAGENTS.mdを修正する必要がないと判断した場合も、その理由を最終報告で簡潔に示す。

# メタ認知による作業規約

## 目的

説明を長くするためではなく、正確性を高めるためにメタ認知を使う。既知の事実と仮定を分離し、重要な認識を外部の証拠と照合し、証拠が現在のモデルと矛盾する場合は計画を変更する。

このファイルは横断的な行動規範を定義する。より具体的なリポジトリまたはディレクトリ単位の指示がある場合は、そちらも引き続き適用する。

## 発動条件

`$metacognition` Skill が利用可能で、かつ以下の**いずれか**に該当する場合は使用する。

- アーキテクチャ、設計、責務境界、技術選定に関する判断が必要である。
- 要件に複数の合理的な解釈があり、解釈によって挙動が大きく変わる。
- 変更がモジュール、レイヤー、サービス、その他の重要な境界をまたぐ。
- public API、プロトコル、永続化データ構造、migration、認可・セキュリティ、並行処理、その他の元に戻しにくい契約を変更する。
- 正しさを明確な機械的チェックだけでは確立できない。
- 重要な仮定がまだ検証されていない。
- 現在の方針がすでに失敗した、矛盾する証拠が出た、または修正を繰り返している。
- ユーザーが、単に動く実装ではなく、根本原因分析、レビュー、代替案比較、最適な設計判断を求めている。

format、typo修正、狭い範囲のrenameなど、正しさが明白で安価に検証できる単純な機械作業には、他の発動条件に該当しない限りSkillを使用しない。

Skillが利用できない場合でも、チェック自体を省略せず、同等の確認を直接行う。

## 証拠に関する規律

- **事実（fact）**、**仮定（assumption）**、**未知（unknown）**、**判断（decision）**を区別する。仮定を暗黙に事実へ昇格させない。
- ユーザー要求、リポジトリ、ソースコード、テスト、compiler/type checker、runtime挙動、ログ、公式ドキュメントから得られる直接的証拠を優先する。
- 「もっともらしい」「自信がある」だけでは証拠として不十分とみなす。
- 重要な主張については、何がそれを支持する証拠なのか、何を観測すれば反証できるのかを把握する。
- 新しい証拠が現在の計画と矛盾する場合は、モデルと計画を更新する。すでに工数をかけたという理由だけで以前の選択を守らない。

## 検証に関する規律

重要な作業を完了と宣言する前に、以下を行う。

- 成果を要求された挙動と受け入れ条件に再対応付けする。
- 変更対象に対して実行可能な中で最も強い機械的チェックを行う。
- diffまたは成果物を確認し、意図しない変更がないかを見る。
- 必要に応じて失敗経路やedge caseを確認する。
- 関連するチェックを実行できなかった場合は明示する。未実行のチェックを成功したものとして扱わない。

build、test、lint、validationの具体的なコマンドは、既存のプロジェクトコマンドおよび、より近い階層にある`AGENTS.md`の指示を使用する。

## 独立レビューの発動条件

以下の**いずれか**に該当する場合、最終化する前に少なくとも1つの独立したsubagentレビューを行う。

- アーキテクチャまたは責務境界を変更している。
- public contract、永続化データ、migration、authentication/authorization、security、concurrency、data lossのリスクが関係する。
- 重要な要件が曖昧なままだが、実装を進める必要がある。
- 正しさを判定する強い機械的oracleが存在しない。
- タスクが広く、実装担当agentが初期解釈にanchoringしている可能性がある。
- 検証によって予想外または矛盾する証拠が得られた。

コードベース上の事実が不明確な場合は、必要に応じて読み取り中心の調査を`explorer` subagentへ委譲する。

独立レビューでは、プロジェクトに設定済みのreviewer subagentがあればそれを優先する。存在しない場合は、レビュー専用の明示的なpromptで別のsubagentを起動する。そのsubagentには承認ではなく反証を求める。レビューに必要な目標、制約、関連する成果物/diff、証拠を渡し、親agentが選んだ方針を正解であるかのように提示しない。

必須レビューの結果が返るまで最終化しない。reviewerの指摘も無条件には受け入れず、証拠と照合して検証する。

すべてのタスクで機械的にsubagentを起動しない。この条件に該当した場合の既定値は独立reviewer 1体とし、異なるリスク領域に別々の専門性が本当に必要な場合だけ追加する。

## 人間へのエスカレーション

リポジトリ、ツール、テスト、公式ドキュメントで解決できる技術的な未知は、自律的に解消する。

未解決の選択が、ユーザー自身が決めるべきproduct intent、business policy、破壊的または不可逆な承認、証拠だけでは決められない価値判断に依存する場合はユーザーへ確認する。調査が面倒という理由だけで質問しない。

人間に判断を求める前に、AIが作成した資料をユーザーが未読である可能性を前提に、次を簡潔に説明する。

- その判断が関わる機能・用語と、現在の状態
- 何が未確定で、なぜAIだけでは確定できないのか
- 各選択肢で何が変わるか（利用者・公開契約・後続作業への影響）
- 推奨する選択肢と、その根拠・他案を採らない理由

前提説明なしに、資料内の用語、field名、内部設計の差異だけを示して承認を求めない。説明後も判断に必要な情報が不足する場合は、選択肢を増やす前に不足点を補う。

## 完了基準

重要なタスクは、以下をすべて満たした場合のみ完了とする。

1. 実装結果が明示された目標と制約を満たしている。
2. 重要な仮定が検証済み、または未解決として明示されている。
3. 関連するチェックを実際に実行し、その結果を把握している。
4. 必須の独立レビュー指摘が、解決済み、証拠付きで棄却済み、または残存リスクとして明示されている。
5. 最終回答で、検証済みの結果と残っている不確実性を区別している。

private chain-of-thoughtは公開しない。伝えるのは、判断に必要な結論、証拠、仮定、検証結果、未解決リスクだけとする。
