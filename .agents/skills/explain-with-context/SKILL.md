# 前提を省略せず説明する

## 目的

利用者が未定義の用語を推測せず、各設計要素が必要な理由と判断への影響を理解できる文章を作る。短さよりも判断に必要な情報の完全性を優先し、同じ説明規則を成果物、作業セッション記録、利用者への返答へ一貫して適用する。

## 必ず守る規則

1. 用語集だけを追加して説明完了としない。変数、属性、レコード、スキーマ、列挙値を記載する各箇所で、意味と必要な理由を都度併記する。
2. 英語、略語、横文字、比喩的な呼び名を説明の代わりに使わない。正確な機械識別名を残す場合は、初出時に日本語の役割名、具体的な意味、必要な理由を併記する。
3. 「一般に分かるはず」という前提で省略しない。読者がその文章だけで判断できない用語は、その場または直前で説明する。
4. 説明のための独自用語をむやみに増やさない。日本語へ置き換えて意味が保てる場合は置き換える。比喩を残す場合は、保存する値や実際の処理へ言い換える。
5. 利用者への質問を作業ファイルだけへ記載しない。質問に必要な情報と質問本文の全体を、利用者へ返す会話にも記載する。「ファイルを参照してください」で代用しない。
6. 会話側だけを短縮しない。作業セッション記録に書いた前提、理由、影響、判断基準、推奨のうち、判断に必要な内容を利用者への返答から落とさない。
7. 利用者が明示的に承認するまでCommit（Gitへ変更履歴として保存する操作）しない。「完了」「終了」「準備」「反映」などをCommitの承認と解釈しない。

## 説明の作成手順

### 1. 読者が判断する対象を特定する

文章を読む人が何を理解し、何を選択または確認する必要があるかを先に特定する。設計者だけが知っている元資料、会話履歴、業界慣習を暗黙の前提にしない。

### 2. 用語を分類して説明する

初出の用語が次のどれかを明記する。分類名そのものも、必要なら文章中で説明する。

- ドメイン知識（対象分野の知識）: 設計対象となる業務・知識分野について成り立つ内容であり、利用者が知っているかを評価できる事実、規則、手順、判断など。
- ドメイン用語（対象システム固有の用語）: 対象システム内の概念や記録形式に付けた名前。名前やレコード自体は知識ではなく、知識を表現・整理するための設計要素である。
- 一般的な設計用語: スキーマ、属性、参照整合性など、特定システムに限定されない設計上の語。
- 実装上の識別名: プログラムや保存データが機械的に区別するための正確な名前。識別名だけを説明として提示しない。

`Runtime`（実行環境または実行主体）、`Concept`（概念）、`KnowledgeAssertion`（知識判定用の命題）のように、英語だけでは複数の意味へ解釈できる語は、そのシステムで何を指し、何を指さないかを明記する。「検索アンカー」のような比喩は、たとえば「検索時に照合する索引語」のように、保持する値と用途が分かる表現へ直す。

### 3. 設計要素の説明を使用箇所へ置く

スキーマ、レコード、変数、属性ごとに、少なくとも次を同じ箇所で説明する。

- 何を表すか。
- なぜ必要か。存在しない場合に何を判断、追跡、検証できなくなるか。
- どの値を許可し、どの値を禁止するか。
- 他の似た項目と何が違うか。
- 値が任意または条件付きなら、どの状況で存在するか。

必要な理由を表の末尾へまとめたり、章冒頭の一般論だけで代用したりしない。属性表なら各行へ「必要な理由」を書く。スキーマ説明なら、そのスキーマの直下へ必要性を書く。

### 4. 列挙値と分類条件を説明する

列挙値は、値の一覧だけで終わらせない。各値について日本語の意味、該当する状況、該当しない状況、紛らわしい他の値との境界を説明する。

一つの列挙へ異なる分類軸を混ぜない。たとえば「誰が行ったか」を表す値に、「どの方法で取り込んだか」を表す値を混ぜない。行為主体、作成者、取得方法、出典種別、処理段階などが異なる場合は、別の項目として説明する。

### 5. 文書全体の説明不足を点検する

利用者が指摘した一語だけを直して終えない。同じ文書内の英語、略語、固有名、スキーマ名、属性名、列挙値、比喩的表現を再走査し、同種の説明不足をまとめて解消する。

次を確認する。

- 定義より前に用語を使用していないか。
- 「元内容」「対象」「状態」「主体」など、何を指すか曖昧な普通名詞が残っていないか。
- 意味は書かれていても、必要な理由が欠けていないか。
- 値の一覧はあっても、各値を選ぶ条件が欠けていないか。
- ドメイン知識と、知識を記録するための用語・データ構造を混同していないか。
- 質問への回答によって確定した設計が、制約や属性説明にも反映されているか。

## 利用者へ質問する手順

設計判断が元資料や既存資料から確定できない場合だけ質問する。質問前に、安全な読取り調査で確定できないか確認する。

質問には、次の内容を順番に含める。

1. 用語と前提知識: 質問を理解するために必要な概念を日本語で定義する。
2. 未確定事項: 何が資料から決まらず、利用者の判断を必要としているかを示す。
3. 質問する理由: 回答がどの設計や動作を変えるか、誤ると何が起きるかを示す。
4. 選べる考え方と影響: 各案で可能になること、制限されること、将来の影響を示す。
5. 判断基準: 利用者が何を重視すると各案になるかを示す。
6. 現在の推奨: 推奨する案と、その根拠を示す。判断材料が不足する場合は不足を明記する。
7. 質問本文: 利用者に何を答えてほしいかを、一つの明確な文で示す。

作業セッションファイルがある場合は、質問全体を回答待ちの質問としてそこへ記録する。そのうえで、利用者への返答にも同じ判断材料と質問本文を記載する。途中経過欄だけに書かず、利用者が実際に読む最終返答にも残す。

利用者が回答したら、回答をセッション記録へ追記し、回答から採用する設計と必要な理由を明記する。回答前の質問と判断材料は履歴として残し、未回答扱いの表現、後で確定するという制約、回答待ちの見出しを確定済みへ直す。

## 利用者へ返す前の確認

次を満たしてから完了を報告する。

- 変更した成果物と作業セッション記録で、説明内容が矛盾していない。
- 利用者への返答だけを読んでも、現在の結論、未回答の質問、次に必要な判断が分かる。
- 未回答の質問がある場合、その前提、理由、影響、判断基準、推奨、質問本文が会話内にすべてある。
- 新しい用語、変数、属性、スキーマ、列挙値に、意味、必要性、分類条件の欠落がない。
- 利用者のCommit承認がない限り、Commitしていないことを明示する。
