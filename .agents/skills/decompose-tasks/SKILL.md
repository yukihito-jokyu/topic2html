# Decompose Tasks

親タスクを一段下だけに分割し、既存階層との横断整合性を独立検証した後で案を提示する。

## 手順

1. 原典Issue・仕様、議論記録、現在のTask Mapを読む。
2. 現在の親タスクと今回決める階層を特定し、祖先、兄弟、既知の後続タスクも確認する。
3. [分割担当プロンプト](references/decomposition-agent-prompt.md)を全文読み、その指示と今回の入力を分割担当サブエージェントへ渡す。
4. 分割案を受け取ったら、[妥当性確認担当プロンプト](references/validity-agent-prompt.md)を全文読み、原典と分割案を妥当性確認担当サブエージェントへ渡す。
5. 両者の結果を統合し、今回の候補と既存の承認済みタスクを横断して、責務、成果物、粒度、階層、工程、依存関係の矛盾を確認する。
6. タスクごとに着手依存、完了・Merge依存、出力を受け取る後続タスクを区別してDAG化する。循環、隠れ依存、不要な直列化、設計確定前の実装開始、親の開始依存と完了依存の混同を確認する。
7. 実装を並行化する可能性がある場合は、git worktreeの共通起点、File・Directory所有、Schema、Migration、共通Interface、Registry、DI、Lockfile、生成物、共有Fixtureの単一Owner、Merge順を確認する。安全に分離できなければ直列化する。
8. 複数タスクの設計整合を確認するだけの工程は、独立成果物がなければ子タスクにせずGateまたはMilestoneとして依存図に表す。
9. 定義済み事項の再検討だけを目的とする候補を削除・統合・移動する。技術選定、設計、実装、検証は、親の完了に必要で原典上未確定・未実施の場合だけ独立させる。
10. 提案と理由を議論記録へ「議論中」として追記する。承認済み構造の修正候補は旧決定を残し、対象、問題、修正案、理由、影響範囲、再承認単位を記録する。
11. ユーザーには各項目を必ず「タスク名」「分割した理由」の順で簡潔に提示する。既存構造の修正案がある場合は、新規分割案と分けて先に示す。
12. 承認後に議論記録とTask Mapを更新する。Task Mapには直接依存だけでなく、必要に応じてGate、着手条件、完了・Merge条件、worktree実行規則を記録する。承認済みタスクの修正は、再承認前に確定構造へ反映しない。
13. 現在の親タスクの小分類を完了してから次の中分類へ進む。ただし横断矛盾が後続分割へ影響する場合は、修正案の議論を先に行う。

## 判定原則

- 原典で結論済みの設計判断を、再議論だけのタスクにしない。
- 仕様が十分でも、未実施の実装・検証・成果物作成はタスクになり得る。
- 通常の分割では一度に一階層だけ扱う。横断監査では全階層を確認できるが、新しい子孫階層を同時に確定しない。
- 同一階層のタスクは重複を避け、完了条件を独立させる。
- 別の親タスクに属する候補は、削除せず移動先を記録する。
- 分割担当と妥当性確認担当は別サブエージェントにする。
- 承認は、その時点の情報に基づく構造確定であり、将来の整合性を保証しない。
- 承認済みであること自体を妥当性の根拠にしない。後続分割で矛盾が判明したら再編案を提示する。
- 親の名称・成果物と子の総和、隣接タスクとの責務境界、工程順序、直接依存、横断要件の所有者を毎回確認する。
- 設計と実装を含む親では、関連する設計が横断的に確定する前に本番実装へ進む経路がないか確認する。
- 直接依存は、着手を止める条件と、完了・Mergeだけを止める条件を混同しない。MockやFixtureで先行可能なら過剰待機を避ける。
- 親タスク間の依存は、その親の開始条件か完了条件かを明記し、子タスクの先行設計と循環しないようにする。
- worktree並行性は責務の違いだけで判断せず、変更所有が分離できることを条件にする。共有Fileを複数Taskが変更する場合は単一Ownerまたは直列Mergeにする。
- 修正時は承認履歴を上書きせず、旧構造から新構造への変更理由を追跡可能にする。

## 出力形式

```markdown
### <タスク名>

分割した理由：  
<原典との差分と、この単位で独立させる理由>
```
