# メタ認知

このSkillは、現在のタスクモデルを観測可能かつ修正可能にするために使う。目的は長く考えることではない。根拠のない認識を検出し、判断を分ける証拠を収集し、証拠が要求するなら実行方針を変更することが目的である。

ユーザーまたは他の適用可能な指示が要求しない限り、この過程を記録するためだけのドキュメントをリポジトリに新規作成しない。作業中の表現は簡潔に保つ。

private chain-of-thoughtは公開しない。報告するのは、簡潔な結論、証拠、仮定、判断、検証結果、未解決リスクだけとする。

## 中核となる不変条件

1. **認識状態を分離する。** 事実、仮定、未知、判断は別物である。
2. **外部証拠を自信度より優先する。** 根拠のない自信ある回答は、依然として未検証である。
3. **重要な仮定には反証経路を持つ。** 何を観測すればその仮定が誤りだと分かるかを把握する。
4. **計画は修正可能である。** 新しい証拠によって以前の作業が無効になる場合がある。sunk costは悪い方向を維持する理由にならない。
5. **独立レビューの目的はanchoringを外すことである。** reviewerは現在のモデルを確認するのではなく、なぜ間違っている可能性があるかを探す。
6. **メタ認知には終了条件が必要である。** リスクを実質的に下げられる最小限のレビューを使い、無限の自己レビューに陥らない。

## ワークフロー

### 1. タスクを定式化する

重要な判断を行う前に、簡潔なタスクフレームを確立する。

```md
## タスクフレーム
- 目標:
- 受け入れ条件:
- 制約:
- 対象外:
```

これらはユーザー要求と適用されるプロジェクト指示から導出する。product requirementを勝手に作らない。情報が欠けていても結果に大きく影響せず、後から戻せる場合は、合理的なdefaultを選び、それを仮定として記録する。

### 2. 認識マップを作る

判断に関係する項目だけを表現する。

```md
## 認識マップ
### 事実
- [検証済みの事実] — 証拠: <ユーザー要求 | file/symbol | test | command | runtime | 公式document>

### 仮定
- [仮定] — 誤っていた場合の影響: <影響> — 検証: <確認方法>

### 未知
- [未知] — 重要度: blocking | important | non-blocking — 次に見る証拠: <調査先>

### 判断
- [すでに行った判断] — 根拠: <証拠/制約> — 可逆: yes | no
```

ルール:

- 直接的な証拠がある場合のみ**事実**へ置く。
- 推測したリポジトリ挙動は、source、test、runtime evidenceで確認されるまで**仮定**として扱う。
- あらゆる不確実性を列挙しない。実装、安全性、成果の受け入れ可否を変えうる未知だけを残す。
- 仮定の影響が大きく、安価に検証できるなら、先に検証してから進む。

### 3. 価値の高い未知を解消する

判断リスクを最も大きく下げる順序で調査する。

該当する場合は、次を優先する。

1. 明示されたユーザー要求と受け入れ条件。
2. 適用される`AGENTS.md`とリポジトリdocument。
3. source code、type、schema、test、call site。
4. compiler、type checker、static analysis、test runner、runtime observation。
5. version固有または外部挙動についての公式document。

広く読む前に、対象を絞ったリポジトリ検索を行う。探索によってmain contextが汚染される、または広範囲のscanが必要な場合は、読み取り中心の調査を`explorer` subagentへ委譲し、file/symbolの証拠を伴う調査結果だけを返させる。

利用可能な証拠で解決できる技術的な質問を、ユーザーへ尋ねない。

### 4. 重要な判断を反証する

非自明な設計判断では、以下を問う。

- 現在の方針が正しいためには、何が真である必要があるか。
- その前提のうち、何が検証済みで、何が仮定か。
- 最も強い合理的な代替説明または代替設計は何か。
- 現在の計画が見落としうるfailure modeは何か。
- 何を観測したら方針を変えるべきか。

代替案は、実質的に異なり、判断に影響する場合だけ生成する。機械的に決まる変更のために無理に選択肢を作らない。

代替案が重要な場合は、一般論の好みではなく、実際の制約に照らして比較する。

```md
## 判断チェック
- 判断:
- 選択肢A:
- 選択肢B:
- 関連する評価基準:
- 証拠:
- 採用する方向:
- この評価基準では棄却案が劣る理由:
- 判断を変える証拠:
```

最初に提案された、またはすでに一部実装されているという理由だけで選択肢を採用しない。

### 5. 最終化前に検証計画を決める

重要な主張ごとに、実行可能な中で最も強いoracleを選ぶ。

例:

- 構造的な互換性にはcompile/type-check。
- 挙動には対象を絞ったtest。
- 境界間の相互作用にはintegration/e2e test。
- 強制可能なinvariantにはstatic analysisまたはlinter。
- 永続化データにはschema/migration check。
- bugにはruntimeでの再現。
- architectureやdependencyに関する主張にはsource/call-site inspection。
- 外部API/versionに関する主張には公式document。
- 意図しないscope拡大にはdiff inspection。

testが通ったことは、そのtestが実際に確認した範囲だけを証明する。狭いチェックを広い主張へ一般化しない。

強い機械的oracleが存在しない場合は、独立レビューを強め、残存する不確実性を明示する。

### 6. モデル違反を監視しながら実行する

実装中、以下の出来事を「停止して認識マップを更新すべきsignal」として扱う。

- リポジトリの実際の挙動が仮定と矛盾する。
- 計画で予想していない理由でtestが失敗する。
- 予想外のlayer/moduleに触れる必要が出た。
- local変更のはずがpublic contractを変える。
- 新しいedge caseによって受け入れモデルが崩れる。
- 方針を成立させるためにpatchを繰り返す必要がある。

根本となるモデルを変えないまま、矛盾する証拠をpatchで回避しない。まず該当する仮定または判断を再定式化する。

### 7. 必要な場合に独立レビューを発動する

適用される`AGENTS.md`が要求している場合、独立レビューは必須である。また、影響が大きい、機械的検証が弱い、またはanchoring riskが高い場合にも適している。

既定では独立reviewerを1体使う。securityとdomain correctnessのように、異なる懸念が明確に存在する場合だけ追加する。

プロジェクト固有のreviewer agentが存在する場合はそれを優先する。存在しない場合は別のsubagentを起動し、レビューのみを実行し、fileを変更しないよう指示する。

以下のようなpromptを使う。

```md
この作業を独立してレビューしてください。親agentの方針が正しいと仮定せず、fileは編集しないでください。

目標:
<goal>

受け入れ条件と制約:
<constraints>

関連する証拠・成果物:
<files, diff, tests, commands, docs>

現在の解を反証することを試みてください。特に以下を探してください。
- 誤っている、または隠れている仮定。
- 要件との不一致。
- architecture/responsibilityの誤り。
- 挙動のregressionとedge case。
- 不足している、または誤解を招く検証。
- 現在の方針が早期に排除してしまった、実質的により良い代替案。

指摘は影響度の高い順に返してください。各指摘には具体的な証拠と、可能なら検証方法を含めてください。重要な問題が見つからなかった場合は、そのことを明示し、何を確認したかも記載してください。
```

anchoringを減らすため、reviewerには問題、制約、証拠、最終的な成果物/diffを渡す。親agentの解がなぜ正しいと思われるかを説得的に説明する文言は避ける。

### 8. レビュー指摘を照合する

重要なreviewer指摘ごとに、以下を行う。

1. 指摘された証拠を確認する。
2. valid、invalid、unresolvedのいずれかに分類する。
3. validならタスクモデルと実装を変更する。
4. invalidなら好みではなく証拠によって棄却する。
5. unresolvedで影響が大きいものは隠さず明示する。

validな指摘によって中核となる仮定または設計判断が変わる場合は、影響範囲の検証だけを再実行し、必要なら焦点を絞ったfollow-up reviewを1回行う。理由なく全工程を最初からやり直さない。

### 9. 最終メタ認知チェックポイント

完了を宣言する前に確認する。

```md
## 最終チェックポイント
- 目標を満たした: yes | no | partially
- 検証済みの重要な仮定:
- 実際に実行した検証:
- 独立レビュー: not required | completed
- 対応済みの指摘:
- 残存する不確実性/リスク:
```

必須チェックが失敗した、または未実行の場合は完了と宣言しない。「未検証」と「検証した結果、誤りだった」を区別する。

最終的なユーザー向け回答には、ユーザーの判断や信頼度に影響する部分だけを含める。通常は実装結果、主要な検証証拠、未解決リスクであり、チェックポイント全文ではない。

## リスクと作業量の制御

このSkillはタスクに比例した強さで使う。

### 軽量パス

範囲は限定されているが、重要な仮定または設計判断が1つ存在する場合に使う。

- タスクフレーム。
- 主要な仮定を検証。
- 実行。
- 機械的チェックを実行。
- 他のgateが要求しない限りsubagentは使わない。

### 標準パス

要件または設計に、相互作用する複数の制約がある場合に使う。

- タスクフレーム + 認識マップ。
- 重要な未知を解消。
- 実質的に異なる代替案を比較。
- 検証計画。
- gateが発動した場合は独立レビュー。

### 高影響パス

元に戻しにくい契約、security/auth、永続化データ/migration、concurrency、architecture boundary、または検証が弱い場合に使う。

- 標準パス。
- 独立レビューを原則実施する。
- 異なるリスク領域がある場合だけreviewerを分ける。
- 残存する不確実性を明示する。

agent自身が申告する自信度だけを理由に、passの強度を下げてはならない。

## アンチパターン

以下を行わない。

- 新しい証拠なしに「そう思う」を「検証済み」へ変える。
- 親agentの解へ誘導するsummaryを付けてreviewerへ「これは正しいか」と尋ねる。
- 明確に異なる理由なしに、複数agentへ同じレビューを繰り返させる。
- 価値の高い不確実性に対処する代わりに、大量の内省文章を生成する。
- 中核となる仮定が崩れた後もpatchで方針を延命する。
- test、linter、reviewer、documentationのどれかを絶対視する。証拠が矛盾する場合は照合する。
- code、tool、公式documentで解決できる問題をユーザーへ質問する。
- 実行できなかったチェックを隠す。
- private chain-of-thoughtを公開する。

## 成功条件

必要な場面で、このSkillによって少なくとも以下のいずれかが起きれば成功とみなす。

- 根拠のない仮定が、手戻りを生む前に検証または修正される。
- 曖昧な要件が技術的な事実と分離される。
- より良い証拠が現れたため設計判断が変更される。
- 独立reviewerが実装時のcontextでは見落とした問題を発見する。
- 検証不足のため「成功」という主張が引き下げられる。
- 最終実装が、初期計画より強い外部証拠によって裏付けられる。

これらの介入が不要な場合は、十分な最小限の検証で終了し、ループを不必要に延長しない。
