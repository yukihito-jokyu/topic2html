# タスクを議論し独立レビューする

## 目的

利用者が前提知識を推測せずに判断できる形でTaskを進め、現在の成果物がIssue #1と直接の後続Issueに矛盾しないかを、独立した別サブエージェントの証拠付きレビューで確認する。現在の成果物を後続へ渡せることと、後続Issueの全依存が揃って実際に着手できることは別に判定する。

ここで「直接の後続Issue」とは、現在のTaskの成果物を着手条件または入力として明記している次段階のIssueを指す。Issue番号が現在のIssueより大きいという理由だけでは後続に分類しない。

## 用語と前提知識

- Task Issue（実行対象の課題）: GitHub上で管理する、独立した完了条件を持つ最小の作業単位である。議論と変更の範囲を限定するために必要である。
- Issue #1（要求の原典）: このプロジェクトで実現する利用者要求を記録したGitHub Issueである。個別Taskの成果物が、元の目的から外れていないか確認するために必要である。
- Task Map（作業構成表）: 大分類から実行単位までのTask、担当成果物、依存関係をまとめた現在の計画である。現在のTaskの位置を確認するために必要である。
- 接続台帳: 成果物を作るTaskと、その成果物を入力として使うTaskの対応表である。現在のTaskから直接の後続Issueを漏れなく逆引きするために必要である。
- 決定記録: 利用者が承認した変更内容、理由、影響範囲を履歴として残す文書である。現在のTaskへ適用する判断を確認するために必要である。
- worktree（分離作業ディレクトリ）: 一つのGitリポジトリからTask専用の作業場所を分ける仕組みである。他Taskの未完了変更を混ぜないために必要である。
- branch（変更履歴の作業系列）とHEAD（その系列の現在位置）: どのTask用の履歴で、どのCommitまでを含むかを識別する値である。別Taskや誤った起点で作業する事故を防ぐために必要である。
- Gate（次工程へ進む前の確認条件）: 設計確定など、後続作業を始める前に満たす必要がある条件である。未確定の前提に基づく実装を防ぐために必要である。
- 成果物Owner（変更責任の所在）: 各Taskが作成・変更してよいファイルや設計領域の担当である。並行Task同士の競合と責任の混在を防ぐために必要である。
- Commit（Gitへ変更履歴として保存する操作）とstaging（次のCommit候補として変更を一時登録する操作）: 成果物を履歴へ確定する段階を区別する語である。利用者からCommit実行の明示指示を受ける前に、変更を確定または確定準備しないために区別する。

## 必須の併用スキル

作業開始時に `$explain-with-context` の `SKILL.md` を全文読み、次のすべてへ適用する。

- 利用者への途中報告と最終回答
- 利用者へ判断を求める質問
- 仕様書、設計書、データ構造、変数、属性、列挙値などの成果物
- `.codex/task-session.local.md` の質問・回答・判断記録

英語名や専門用語だけを提示せず、その場で日本語の意味、必要な理由、該当条件、似た項目との違いを説明する。Commitとstagingは、後述のCommit実行許可を得るまで行わない。

## 必須の役割分離

調査、成果物作成、独立レビューを、互いに異なるサブエージェントへ順に依頼する。メインエージェントがこれらを兼任せず、次の責務だけを担う。

- 作業全体を調整し、各担当へ必要な元資料と確定済み判断を渡す。
- 利用者へ途中経過を説明し、設計判断を必要とする質問と回答を管理する。
- 各担当の報告を元資料と照合し、最終確認、Commit承認、完了報告を管理する。

各担当を次の制約で起動する。

1. 調査担当を読取り専用で起動する。開始時の確認に必要な元資料を調べ、確定事項、差異、未確認事項、判断が必要な事項を証拠付きで報告させる。ファイル、Issue、Gitの履歴や登録状態を変更させない。
2. 実装担当を調査担当とは別に起動する。調査で確認した証拠と利用者が承認した判断を渡し、成果物Ownerと書込み可能なPathの境界内で成果物作成とTask固有の検証を行わせる。境界外の矛盾は変更せず報告させる。
3. レビュー担当を調査担当および実装担当とは別に、読取り専用で起動する。後述の独立レビューを行わせ、ファイル、Issue、Gitの履歴や登録状態を変更させない。

役割間の先入観の漏洩を抑える。各担当には、その役割に必要な元資料、確定済み判断、直前担当が示した検証可能な証拠だけを渡す。メインエージェントや他担当の期待する結論、推測、レビューで見つけてほしい指摘は渡さない。再レビューでは修正箇所を特定できる事実だけを追加し、期待する判定を指示しない。同じサブエージェントを複数の役割へ再利用しない。

必要なサブエージェントを起動できない場合、メインエージェントが代行して完了扱いにしない。利用できない役割、未実施の工程、残る影響を利用者へ伝え、作業を未完了として停止する。

## Commit実行許可

成果物、方針、設計判断、Skill修正案への「承認」や、対象を特定しない一般的な「承認」を、Commitまたはstagingの許可と解釈しない。

1. Commit対象ファイルと予定Commitメッセージを利用者へ提示する。
2. 提示後に、利用者が対象変更のCommit実行を明示的に指示した場合だけ、対象ファイルをstagingしてCommitする。
3. Commitを指すか、対象が何か、実行を求めているかのいずれかが曖昧な場合は未承認として扱い、stagingもCommitも行わない。

Commit実行の明示指示は、成果物や修正案の承認とは別に確認する。実装担当やレビュー担当へCommitとstagingを行わせず、メインエージェントが許可の確認と実行を管理する。

## 開始時の確認

1. `.codex/task-session.local.md`、現在のTask Issue、現在のTask Mapを読む。
2. 現在のbranch、HEAD、依存Task、Gate、成果物Owner、書込み可能なPathを照合する。
3. Issue #1を読み、現在のTaskが満たすべき利用者要求、用語、状態、受け入れ条件を抽出する。
4. Issueの依存関係、現在のTask Map、`docs/task-connections.md`（成果物を作るTaskと利用するTaskの接続台帳）から直接の後続Issueを特定し、後続が現在の成果物へ期待する入力と開始条件を抽出する。
5. Issueが特定の決定記録を参照している場合は、その記録も読み、承認済みの変更理由と影響範囲を確認する。
6. Issue、現在のTask Map、作業セッションの差異を見つけた場合は、勝手に意味を追加せず利用者へ報告する。

Issue #1、後続Issue、現在のTask Mapの取得方法が分からない場合も、推測で代用しない。リポジトリ内の対応資料やGitHub Issueを読み取り、確認できなければ未確認と明記する。

## 議論と実行

1. 現在のTaskで確定済みの内容、未確定の内容、今回変更できる範囲を分ける。
2. 資料から安全に確定できる内容は質問せず進める。
3. 利用者の判断が必要な場合は、`$explain-with-context` が定める前提知識、未確定事項、質問理由、選択肢の影響、判断基準、推奨、質問本文を省略せず、会話と `.codex/task-session.local.md` の両方へ記録する。
4. 利用者の回答を、採用した設計、その理由、影響する成果物へ反映する。質問履歴を消さない。
5. 成果物をOwner境界内で作成または変更し、Task固有の検証を実行する。
6. Task範囲外の矛盾を見つけた場合は、変更せず、対象Ownerと次に必要な対応を記録する。

## 独立レビュー

利用者へ完了を返す前、かつCommit前に、最低1つの別サブエージェントへ読取り専用のレビューを依頼する。レビュー担当へファイル、GitHub Issue、Gitの履歴や登録状態を変更させない。自分の結論や期待する答えを渡さず、現在のTask Issue、Issue #1、直接の後続Issue、現在のTask Mapと接続台帳、Issueが参照する決定記録、変更成果物、`.codex/task-session.local.md`、現在のbranch・HEAD・`git status`・差分という元資料を渡す。

レビューでは、少なくとも次を確認させる。

- Issue #1の要求、用語、状態、受け入れ条件との矛盾または欠落
- 直接の後続Issueが必要とする契約、入力、依存関係、開始条件との矛盾または引継ぎ漏れ
- 現在のTask Issueと現在のTask MapのOwner、範囲、依存関係、Gateとの整合
- 成果物内の説明不足、型・制約・分類条件・必要理由の欠落、内部矛盾
- Task固有の受け入れ条件と検証結果の不足
- 未承認Commit、範囲外変更、次のIssueへ判断を先送りした未解決事項の有無
- 後続Issueごとの成果物受渡し可否と、他の依存Taskを含む現在の着手可否の混同

レビュー結果は次のいずれかで分類し、根拠となるIssue、ファイル、該当箇所を示させる。

- `verified`（問題なし）: 根拠を確認でき、修正が不要である。
- `revise`（修正が必要）: 現在のTaskの範囲内で直す必要がある。
- `reject`（指摘を採用しない）: 指摘は元資料と一致せず、採用しない理由を説明できる。

`revise` が一つでもあれば成果物を修正し、修正箇所を明かしたうえで再レビューを依頼する。Commit前に必要な `revise` がなくなるまで完了扱いにしない。サブエージェントを利用できない場合はレビュー済みと主張せず、その事実を利用者へ伝えて作業を完了扱いにしない。

## 完了条件

次をすべて満たした場合だけ、Commit直前まで完了したと報告する。

- Task固有の成果物と検証が完了している。
- Issue #1、現在のTask Issue、現在のTask Map、直接の後続Issueに未説明の矛盾がない。適用した決定記録は追跡できる。
- 独立レビューの `revise` が残っていない。
- 後続Issueが開始時に必要とする確定事項と証拠が明記されている。
- 直接の後続Issueごとに、今回の成果物を渡せるかと、全依存を含めて現在着手できるかを分けて記録している。
- 未回答の質問がない。ある場合は、前提から質問本文までを会話と作業セッションへ明記している。
- Commit対象ファイルと予定Commitメッセージを提示し、利用者からCommit実行の明示指示を受けていない限り、Commitもstagingも行っていない。

最終回答では、変更した成果物、実行した検証、独立レビューの結論、未解決事項、Commitの有無を端的に伝える。
