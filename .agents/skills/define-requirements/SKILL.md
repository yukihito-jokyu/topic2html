# 要件定義を進める

ユーザーの言葉から目的と期待成果を明らかにし、確認済みの事実と未決事項を追跡しながら要件定義を合意する。実現手段を決める詳細設計は扱わない。

## 必須リソースを読む

作業開始時に次のファイルを最後まで読む。

- [reviewer-protocols.md](references/reviewer-protocols.md): サブエージェントの役割、入出力、判定基準
- [artifact-templates.md](references/artifact-templates.md): 要件定義書と議論マップの形式

## 不変ルール

1. ユーザーへの質問は1メッセージにつき1問、1論点だけにする。
2. 質問を提示する前に、必ず質問妥当性レビュアーの `PASS` を得る。
3. ユーザーから実質的な回答を得るたびに、必ず充足度監査を実行する。
4. ユーザーへ次の質問を出す前に、要件定義書と議論マップを更新する。
5. 確認済み、推定、未確認、対象外を混同しない。推定を確定事項として記載しない。
6. 詳細設計の論点を質問しない。必要な場合は期待成果、外部から観測できる振る舞い、業務上の制約へ言い換える。
7. サブエージェントを利用できない場合は代行レビューを装わず、保護手順を実行できないことをユーザーへ伝えて作業を止める。
8. ユーザーが中止または保留を求めた場合を除き、未解決の重大事項がなくなるまで一問一答を続ける。

## 要件定義と詳細設計の境界

要件定義では「なぜ必要か」「誰が使うか」「何を実現するか」「どの状態なら成功か」を扱う。

扱ってよい論点:

- 背景、目的、期待する成果、成功指標
- 利用者、関係者、利用状況、現状の課題
- 対象範囲と対象外、優先順位
- 外部から観測できる機能・振る舞い、業務ルール、例外
- データの意味、保持・監査・権限に関する業務上の要求
- 性能、可用性、セキュリティ、アクセシビリティなどの測定可能な品質要求
- 制約、依存関係、前提、リスク、受け入れ基準

扱わない論点:

- アーキテクチャ、モジュール・クラス・コンポーネント分割
- API、DBスキーマ、内部データ構造、アルゴリズム
- ライブラリ、フレームワーク、実装方式、デプロイ構成
- ピクセル単位の画面配置、内部イベント設計、実装タスク分解

ユーザーが自発的に実装案を示した場合は、その案が変更不能な制約かを確認する必要があるときだけ要件レベルに言い換える。単なる案は議論マップの「詳細設計へ持ち越す論点」に記録し、掘り下げない。

## 成果物

最初の依頼から短い `<topic-slug>` を決め、次を作成する。既存ファイルがある場合は継続更新し、上書きで情報を失わない。

- `docs/<topic-slug>-requirements.md`
- `docs/<topic-slug>-requirements-discussion-map.md`

対象名をまだ決められない場合は、最初の1問で対象と目的を確認してから作成する。成果物は [artifact-templates.md](references/artifact-templates.md) の形式に従う。

## サブエージェントを準備する

セッション開始時に [reviewer-protocols.md](references/reviewer-protocols.md) に従い、次の独立した2役を作成または再利用する。

1. `requirements-completeness-auditor`: 現在の要件が確定に十分かを監査する。
2. `requirements-question-guard`: 次に尋ねる1問が妥当で、詳細設計に踏み込んでいないかを審査する。

両者にユーザーとの会話履歴全体を渡さない。現在の要件定義書、議論マップ、未解決事項、候補質問など、各判定に必要な最小限の情報だけを渡す。主担当の結論を正解として伝えない。

## ワークフロー

### 1. 既存情報を確認する

依頼文と、リポジトリ内にある関連文書を読み、既知の事実、仮定、未解決事項を分ける。対象名が分かれば、テンプレートから要件定義書と議論マップを作成する。

初期ノードを `D-001` とし、依頼の目的を要約する。依頼から確定できない内容は未確認として記録する。

### 2. 充足度を監査する

初回候補質問を作る前、およびユーザーの各回答を成果物へ反映した後に、充足度監査へ現在の成果物を渡す。

- `INSUFFICIENT`: 最優先の不足論点を1つ選ぶ。
- `SUFFICIENT`: 重大な未解決事項がないことを確認し、最終合意へ進む。
- `CONFLICT`: 要件間の矛盾を最優先で解消する。

監査結果は参考意見として記録するが、サブエージェントに要件を勝手に確定させない。

### 3. 次の1問を作る

監査が示した最優先論点について、回答可能な1つの質問文を作る。質問には複数の疑問文や「AとB」のような別論点を束ねない。必要な背景説明は短く添えてよいが、質問文は1つにする。

質問ノードを議論マップへ追加し、現在地をそのノードへ移す。新しい論点は適切な親ノードから分岐させ、単なる時系列の子にしない。

### 4. 質問を審査する

候補質問、対象ノードと親ノード、監査結果、既知事項を質問妥当性レビュアーへ渡す。

- `PASS`: その1問だけをユーザーへ提示する。
- `REVISE`: 指摘を反映して質問を修正し、再審査する。
- `BLOCK`: 質問せず、要件レベルの別論点を選び直して再審査する。

詳細設計に触れる候補は、ユーザーへ見せる前に必ず差し戻す。

### 5. 回答を反映する

次のユーザーターンで回答を受けたら、最初に以下を行う。

1. 回答を、確定事項・仮定・未解決事項・対象外へ分類する。
2. 対応する要件ID、制約ID、受け入れ基準IDを更新する。
3. 議論ノードへ回答の要約と根拠を追記し、状態を更新する。
4. 回答から新論点が派生した場合は同じ親の下または回答ノードの下に追加する。
5. 詳細設計の話題は「詳細設計へ持ち越す論点」に隔離する。
6. 充足度監査へ戻る。

回答が曖昧、矛盾、判断不能の場合も、推測で埋めずに次の1問で解消する。

### 6. 要件を確定する

充足度監査が `SUFFICIENT` と判定したら、未解決事項、矛盾、測定不能な受け入れ基準が残っていないか主担当でも確認する。質問妥当性レビューを通したうえで「この内容で要件定義を確定してよいか」を1問だけ尋ねる。

ユーザーが承認した場合:

1. 要件定義書の状態を `確定` にする。
2. 議論マップの現在地を `要件定義確定` にし、未採用枝と詳細設計へ持ち越す論点を残す。
3. 確定した範囲、主な対象外、残る持ち越し事項を簡潔に報告する。

ユーザーが承認しない場合は、指摘を未解決事項として反映し、充足度監査へ戻る。

## 品質基準

- 各要件がユーザーの発言または明示的な合意へ追跡できる。
- 各機能要件が外部から観測できる結果として書かれている。
- 非機能要件と受け入れ基準が可能な限り測定可能である。
- 対象内・対象外、仮定・事実、要件・実装案の境界が明確である。
- 議論マップを見るだけで、現在地、親論点、分岐、保留、棄却、持ち越しが分かる。
- ユーザーが一度に回答する論点は常に1つである。
